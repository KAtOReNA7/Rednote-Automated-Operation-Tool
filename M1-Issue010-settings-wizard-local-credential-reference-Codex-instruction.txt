七、凭据存储技术决策
--------------------

Windows 生产实现优先采用 Electron safeStorage 的异步 API。

官方参考：

Electron safeStorage：
https://www.electronjs.org/docs/latest/api/safe-storage

Windows DPAPI：
https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata

Electron app paths：
https://www.electronjs.org/docs/latest/api/app

要求：

1. safeStorage 只能在 Electron main process 使用。
2. 必须等待 app ready。
3. 优先使用：
   - safeStorage.isAsyncEncryptionAvailable()
   - safeStorage.encryptStringAsync()
   - safeStorage.decryptStringAsync()
4. 不使用同步 API作为默认实现。
5. 不调用 safeStorage.setUsePlainTextEncryption。
6. Windows 下依赖 Electron 的 DPAPI 保护。
7. 加密 blob 存在 app 专属 userData 子目录，不存在 ProjectDataRoot 内。
8. 数据库只保存不含秘密的 credential reference。
9. UI 和 preload 永远拿不到已保存密钥值。
10. safeStorage 不可用时拒绝保存，返回稳定错误。
11. 不自动降级为明文。
12. 不引入 keytar、云密钥库、远程 vault 或自研主密码。
13. 不把密钥写入 Windows 注册表。
14. 不要求管理员权限。
15. 不把密钥写入系统环境变量。
16. 不把密钥写入 Chromium localStorage、sessionStorage、IndexedDB 或 cookie。
17. 不把密钥写入 renderer 持久状态。
18. 不把密钥放进 Job payload、result、audit 或 error。

Electron 官方说明的真实安全边界必须写进 ADR：

- Windows safeStorage 使用 DPAPI；
- 通常需要同一 Windows 登录凭据，并且通常需要同一台电脑才能解密；
- 它防止其他 Windows 用户直接解密；
- 它不防止同一用户空间中的恶意程序；
- 数据根复制到另一台电脑时密钥不会随之可用；
- 不得宣称硬件保险箱、零知识或绝对安全。

Roadmap 的“操作系统凭据库或本地忽略文件”是二选一。
本轮选择 OS-protected safeStorage 分支即可满足，不实现生产明文忽略文件。

九、加密 blob 生命周期
----------------------

凭据 blob 目录必须是 app userData 下的固定应用子目录。

要求：

1. 目录和文件名由应用常量决定。
2. 槽位到文件名使用固定 allowlist，不接受用户字符串。
3. ciphertext 可保存为二进制或受版本控制的 envelope。
4. envelope 至少包含 format、version、slot、ciphertext 和时间。
5. envelope 不含 data root、base URL、模型 ID 或密钥提示。
6. 写入采用临时文件、sync 和原子/版本化发布。
7. 替换失败时旧 ciphertext 保持可用。
8. clear 只删除精确槽位文件，并需要 UI 明确确认。
9. 不提供删除整个 userData 的 API。
10. 文件损坏返回 CORRUPT，不回显底层 bytes。
11. decrypt 失败返回 REAUTH_REQUIRED 或稳定错误。
12. safeStorage 返回 shouldReEncrypt 时，使用解密结果重新加密并安全替换。
13. re-encrypt 失败时不破坏旧 blob。
14. app 退出时关闭文件句柄。
15. 测试 userData 必须重定向到系统临时目录。
16. 测试结束只清理本次创建的精确临时目录。

不得宣称 JavaScript 字符串能够可靠内存清零。
实际要求是减少复制、缩短生命周期、保存后清空表单状态、不记录、不回显。

十一、数据根定位器
------------------

Issue 008 的 ProjectDataRoot 继续作为唯一数据根实现。

Issue 010 新增一个最小 bootstrap locator，用于应用启动时找到当前项目。

建议位置：

app.getPath("userData") 下的固定应用子目录。

locator 至少包含：

- format
- version
- activeDataRoot
- projectInstanceId
- revision
- updatedAt

locator 不包含：

- 密钥；
- base URL；
- 模型 ID；
- 账号文案；
- 数据库内容；
- 业务正文。

规则：

1. activeDataRoot 是唯一允许的受控绝对路径引用。
2. 业务 SQLite 仍只保存 ManagedRelativePath。
3. 每次启动都重新验证绝对路径和 ProjectDataRoot 根标记。
4. projectInstanceId 必须与根标记匹配。
5. locator 不存在时进入首次设置向导。
6. locator 损坏时进入恢复页面，不自动覆盖。
7. locator 指向的目录缺失时不自动重建。
8. locator 指向非受控根时拒绝。
9. 版本高于当前支持时拒绝。
10. locator 写入必须原子。
11. locator 更新使用 revision 或等价并发保护。
12. 切换根目录前先完整验证新根和数据库。
13. 新根准备成功后才更新 locator。
14. locator 更新失败时旧根保持 active。
15. 不删除、移动、合并或复制旧根。
16. 新空目录初始化失败时不写 locator。
17. 现有合法根可重新打开。
18. 非空无根标记目录继续由 Issue 008 拒绝。
19. 根切换需要 UI 明确确认：
    “不会复制或删除旧目录中的数据”。
20. 本轮不实现自动迁移数据根。

Electron 文档说明 userData 适合应用配置但不适合大型数据。
因此 locator 和加密 credential metadata 可以放在 userData，
全部大型业务数据仍位于用户选择的 ProjectDataRoot。
