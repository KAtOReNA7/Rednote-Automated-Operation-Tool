六、技术结论与官方边界
----------------------

优先使用当前 Electron 43.2.0 / Node.js 24.18.0 内置能力：

- node:fs
- node:fs/promises
- node:path
- node:crypto
- node:stream

默认不引入第三方文件仓库、云 SDK、原生模块或数据库驱动。

官方参考：

Node.js 24 File System：
https://nodejs.org/docs/latest-v24.x/api/fs.html

Node.js Path：
https://nodejs.org/docs/latest-v24.x/api/path.html

Windows 文件命名规则：
https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file

Windows 长路径说明：
https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation

必须遵守以下工程事实：

1. fs/promises 操作本身不会自动序列化同一文件的并发修改。
2. 不得使用“先 exists，再写入”的竞态模式。
3. 新临时文件应通过独占创建或等价机制处理冲突。
4. 大文件必须流式复制和哈希，不能默认整文件读入内存。
5. 同目录临时文件加 rename 可以作为原子发布基础，但不得宣称对所有文件系统、
   所有断电场景都具有绝对持久性。
6. Windows 目录 fsync 行为与 POSIX 不同，不得伪造不存在的持久性保证。
7. 长路径是否可用受应用能力与 Windows 环境共同影响；不得偷偷修改注册表、
   组策略或要求管理员权限。
8. 路径检查必须考虑 Windows 默认大小写不敏感、盘符、UNC、设备路径、
   保留设备名、尾随空格和尾随句点。

十一、ManagedRelativePath
------------------------

数据库和跨包 DTO 的业务文件引用统一使用规范化相对路径。

推荐持久化形式：

- UTF-8 字符串；
- `/` 作为唯一分隔符；
- 不以 `/` 开头；
- 不含反斜杠；
- 不含盘符；
- 不含 URI scheme；
- 不含空段；
- 不含 `.` 或 `..` 段；
- 必须以允许的类别目录开头。

建立品牌类型或不可绕过的构造函数，例如：

type ManagedRelativePath = string & { readonly __brand: unique symbol }

必须提供：

- parseManagedRelativePath
- formatManagedRelativePath
- resolveManagedPath
- relativePathFromManagedAbsolutePath，若确有需要
- isManagedRelativePath

不得允许业务代码用类型断言绕过验证。

拒绝：

- `/absolute/path`
- `C:\absolute`
- `C:drive-relative`
- `\\server\share`
- `\\?\C:\device-path`
- `file:///...`
- `..\escape`
- `a/../../escape`
- `a\..\escape`
- 混合分隔符绕过；
- NUL 和控制字符；
- 只靠字符串 startsWith 判断根目录包含关系。

包含关系至少使用 path.resolve/path.relative，并针对 Windows 做大小写与盘符处理。
对已经存在的路径还要使用 lstat/realpath 或等价检查，拒绝符号链接、junction
和重解析路径把写入引到根目录之外。

必须在 ADR 中诚实说明：

- 这是单用户本地应用的防误用和路径穿越边界；
- Node 跨平台 API 无法把所有 Windows TOCTOU 场景变成绝对不可攻击；
- 因此仓库避免接受任意路径、避免跟随链接，并把外部输入复制为受控文件。


十二、Windows 文件名净化
-----------------------

建立一个确定性、可测试的文件名净化器。

必须处理：

- `< > : " / \ | ? *`
- U+0000—U+001F 控制字符；
- 尾随空格；
- 尾随句点；
- 单独的 `.` 和 `..`；
- Windows 保留设备名：
  CON、PRN、AUX、NUL、COM1—COM9、LPT1—LPT9；
- Microsoft 说明中的 COM¹、COM²、COM³、LPT¹、LPT²、LPT³；
- 保留名加任意扩展名；
- 空结果；
- 超长单段；
- 大小写不敏感碰撞；
- Unicode 和 emoji；
- 中文文件名。

要求：

1. 中文、日文和正常 Unicode 字符尽量保留，不做拼音化。
2. 输出不得以空格或句点结尾。
3. 扩展名与基础名分开处理。
4. 单段长度有明确上限，并为未来目录深度保留路径预算。
5. 截断不能切断 UTF-16 surrogate pair。
6. 净化结果必须确定。
7. 相同显示名发生冲突时使用内容哈希或稳定短哈希消歧。
8. 不依赖 Windows 自动生成的 8.3 短文件名。
9. 不接受调用方传入的目录分隔符作为文件名。
10. 不将原始外部绝对路径写入净化结果或日志。

不要只替换非法字符后直接使用用户文件名。
最终存储名必须具有稳定碰撞保护。


十三、文件写入模型
------------------

至少提供以下底层能力，名称可调整：

1. putBuffer
2. putStream
3. ingestExternalFile
4. openReadStream
5. statManagedFile
6. verifyManagedFile

如实现可控的原子可变写入，也必须使用单独、明确的 API，
不得让普通调用默认覆盖已有文件。

每个成功的不可变文件写入返回有限 descriptor，至少包含：

- category
- managed relative path
- SHA-256
- size in bytes
- sanitized display name 或 storage name
- createdAt

descriptor 不得包含：

- 绝对路径；
- 原外部目录；
- 用户名；
- FileHandle；
- fs 对象；
- 文件正文；
- 密钥。


十四、内容寻址、幂等与并发
--------------------------

来源快照、截图、照片、生成图和导入副本优先采用内容哈希寻址或等价不可变策略。

要求：

1. SHA-256 使用流式计算。
2. 哈希用小写十六进制稳定表示。
3. 同类别、相同内容重复写入返回同一个逻辑文件。
4. 同一文件名但不同内容不得互相覆盖。
5. 两个并发写入相同内容最终只保留一个有效目标。
6. 两个并发写入不同内容均成功且路径不同。
7. 写入先进入目标目录内的应用专用临时文件。
8. 临时文件通过独占创建或等价方式避免冲突。
9. 临时文件与最终文件位于同一文件系统和目录边界。
10. 完成写入后 flush/sync 文件句柄，再关闭，再 publish。
11. publish 失败时旧文件保持不变。
12. 不得先删除旧目标再 rename。
13. 可对 Windows EBUSY、EPERM、EACCES 做有限、可注入、可测试的重试。
14. 重试必须有上限，不得无限等待。
15. 失败或取消后清理本次创建的临时文件。
16. 进程崩溃遗留只允许使用应用专用且可识别的临时文件名。
17. 如实现启动清理，只能删除已验证根目录内、匹配强前缀、达到时间阈值的普通临时文件；
    不得递归清理任意目录。
18. 不得宣称 exactly-once，也不得宣称所有断电场景绝对不会留下临时文件。

对于可变的小型元数据：

- 使用同目录临时文件；
- 写入并 sync；
- 通过 rename 发布；
- 如需要并发更新，使用 expected hash/revision 或进程内目标锁；
- 不允许最后写入者静默覆盖未知并发修改。


十五、外部文件导入复制
----------------------

ingestExternalFile 只做安全复制和登记，不做业务解析。

规则：

1. 输入源路径必须由受信任的上层明确传入。
2. 输入必须是普通文件。
3. 拒绝目录、符号链接、junction、设备、管道和 socket。
4. Windows 下拒绝 UNC、设备命名空间和盘符相对路径作为默认导入源。
5. 不移动、不重命名、不删除用户原文件。
6. 从源文件流式复制到受控临时文件。
7. 复制期间计算 SHA-256 和实际字节数。
8. 支持可配置的最大字节数，并在超过时中止。
9. 复制前后比较必要的 stat 信息；源文件在复制过程中改变时返回稳定错误。
10. 调用方声明的扩展名或 MIME 不能当作已验证事实。
11. 本 Issue 不解析图片、HTML、CSV、Excel、ZIP、PDF 或电子书。
12. 不读取、保存、解析或索引盗版电子书。
13. 不提供通用“导入任意目录”或递归扫描入口。
14. 不把源绝对路径写入数据库、日志、audit 或返回 DTO。
15. 不执行、打开或渲染导入文件。
16. 不调用 shell.openPath、shell.openExternal 或系统关联程序。

可以为类别建立可配置扩展名策略，但不得把未来需要的合法照片、截图或表格
永久锁死。策略与内容验证必须分层，未来 Issue 可在解析前收紧。


十六、大文件与资源边界
----------------------

要求：

1. putStream 和 ingestExternalFile 不使用 readFile 读取完整大文件。
2. 使用 backpressure。
3. 默认并发有上限。
4. 每个操作支持 AbortSignal 或等价取消。
5. 取消不留下最终文件。
6. 文件大小使用安全整数；超过支持范围明确拒绝。
7. 不相信调用方提供的 Content-Length。
8. 计算实际字节数。
9. 哈希、复制和写入错误返回稳定错误码。
10. 不把 stack、绝对路径或文件正文放入用户可见错误。
11. 不在 Electron renderer 执行文件 I/O。
12. 本 Issue 不启动长期 utility process；如现有架构需要，只记录未来大任务应使用
    utilityProcess/JobWorker，不能把大量同步 I/O 放在 UI 线程。


十七、读取、校验与删除边界
--------------------------

只读 API：

- 只接受 ManagedRelativePath；
- 再次做根目录包含验证；
- 只打开普通文件；
- 不跟随符号链接；
- 可返回受控 stream 或有限 metadata；
- 不向 renderer 暴露原始 stream；
- 不把绝对路径写入 DTO。

verifyManagedFile：

- 重新计算 SHA-256；
- 比较期望大小和哈希；
- 文件缺失、损坏、被替换时给出不同稳定错误；
- 不自动修复或删除。

本 Issue 默认不提供：

- 删除整个根目录；
- 任意递归删除；
- 任意绝对路径删除；
- 清空 imports、exports、backups 或 logs；
- 自动垃圾回收；
- 自动删除“孤儿文件”。

如果为了测试或临时文件清理必须删除：

- 只能对系统临时目录内由本测试创建的精确目录执行；
- 或只删除仓库自己创建且强校验的临时普通文件；
- 不得把生产删除 API 暴露给 renderer。


十八、日志基础
--------------

Issue 008 的“管理日志”至少应包含：

1. logs 目录由数据根管理。
2. 提供最小本地结构化日志 sink，或提供已测试的安全日志路径和写入原语。
3. 如提供日志 sink，使用 JSON Lines 或其他明确格式。
4. 日志事件有 UTC 时间、稳定 code、level 和有限 message。
5. 并发 append 由单进程 writer 串行化或使用等价安全设计。
6. 单条日志有大小、深度和字段数量限制。
7. 不保存完整请求头、Authorization、Cookie、API key、password、secret 或 token。
8. 对明显凭据字段和值做递归脱敏。
9. 不保存完整绝对路径；只保存 managed relative path 或稳定错误码。
10. 不保存用户未选择的正文、图片字节或完整 payload。
11. 日志失败不能使业务文件被错误标记为成功。
12. 本 Issue 不做日志上传、远程遥测、Sentry 或云诊断。

如果认为完整日志 sink 应留给后续 Issue：

- 仍必须实现 logs 目录、受控路径和原子/追加写入原语；
- 必须用测试证明原语不会泄露路径和凭据；
- 在 ADR 中明确未实现的日志功能。


十九、导出与备份边界
--------------------

本轮只提供 exports 和 backups 的安全目录与文件原语。

不得实现 Issue 036 的：

- 正式发布包目录结构；
- manifest.json；
- title/body/tags/pinned-comment；
- 图片编号；
- sources.md；
- 整周 ZIP；
- 可发布状态。

不得实现 Issue 044 的：

- 一键备份；
- 一键恢复；
- 根目录全量归档；
- 备份版本升级；
- 恢复覆盖；
- 外部磁盘导出 UI。

允许的数据库备份集成：

1. 保留 Issue 007 迁移前自动备份。
2. 可为 migration runner 增加显式 backupDirectory 注入。
3. 在 ProjectDataRoot 集成测试中，把数据库放到 database/，
   把迁移前备份放到 backups/database/ 或等价受控子目录。
4. 不改变默认迁移语义。
5. 不修改历史迁移内容或校验和。
6. 备份失败时不开始迁移。
7. 备份路径不写入普通业务字段。
8. 本功能不等于 Issue 044 已完成。


二十、数据库路径契约
--------------------

优先选择：

- 业务数据库只保存 ManagedRelativePath；
- 绝对数据根只由未来 Issue 010 的受控本地设置引用；
- 外部导入源绝对路径只在一次操作内存中短暂存在，不持久化。

检查当前 Schema 的全部路径列，至少包括：

- sources.local_snapshot_path
- clips.screenshot_path
- assets.original_path
- assets.processed_path
- post_packages.export_path
- metric_snapshots.import_file_path

如果这些列尚未在数据库层约束 ManagedRelativePath：

1. 添加连续的新迁移，预期版本为 3。
2. 建议名称：
   managed_local_file_paths
3. 不编辑版本 1 或版本 2。
4. 不重新计算历史迁移校验和。
5. 对可空字段保留 NULL 语义。
6. 非 NULL 路径必须：
   - 非空；
   - 使用 `/`；
   - 不以 `/` 开头；

   - 不含 NUL；

如果当前 Schema 已经完整满足上述契约：

- 不要为了“必须有迁移”而制造空迁移；
- 在 ADR、验收映射和最终报告中提供逐列证据。

默认不得新增通用 stored_files/file_catalog 技术表。
只有真实 Schema 无法表达完整性，且 ADR 给出当前需求证据时才允许增加；
不得仅为未来可能有用而增加表。


二十一、文件系统与 SQLite 一致性
------------------------------

SQLite 事务无法和文件系统 rename 形成真正的跨系统原子事务。

本轮必须明确采用的语义，不得声称二者天然原子。

推荐策略：

1. 文件先写入受控临时文件。
2. 完成哈希、大小和 sync。
3. 发布为不可变的内容寻址目标。
4. 数据库事务只保存最终 ManagedRelativePath、哈希和相关元数据。
5. 数据库写入失败时，不删除可能已被其他并发引用的内容寻址文件。
6. 将该文件视为可检测的 orphan。
7. 本 Issue 只提供 orphan 检测报告或测试辅助，不自动删除生产 orphan。
8. 未来垃圾回收必须在有引用扫描、保留期和用户确认后单独实施。

要求测试：

- 文件 publish 成功但数据库失败；
- 数据库约束拒绝绝对路径；
- 重试后同一内容复用；
- 不出现数据库指向半写临时文件；
- 不出现数据库路径逃逸根目录。


二十二、Electron 集成
---------------------

Issue 006 已建立安全桌面壳。

本轮只做最小内部集成：

二十三、Windows 长路径策略
--------------------------

“合理处理长路径”必须用行为证明，不得只写文档。

要求：

1. 内部目录和文件名保持短且确定，避免主动制造深路径。
2. 文件名段有上限。
3. ManagedRelativePath 总长度有明确预算。
4. 根目录打开时执行不破坏数据的能力检查或等价验证。
5. Windows 测试覆盖总路径长度超过传统 MAX_PATH 的场景。
6. 使用多段目录，不创建超过文件系统单段上限的组件。
7. 源码 Node、源码 Electron 和 packaged EXE 至少在当前 Windows 环境中各有实际证据。
8. 不修改 LongPathsEnabled 注册表。
9. 不要求管理员权限。
10. 如果当前系统无法支持目标路径：
    - 在正式写入前返回稳定 PATH_CAPABILITY_UNSUPPORTED；
    - 不留下半初始化数据；
    - 不把系统错误原文和完整路径暴露给 UI；
    - 最终报告如实说明；
    - 不伪造“长路径已通过”。
11. 不宣称所有 Windows 10/11 机器无需系统条件即可无限长路径。
12. Windows 10/11 的最终双机验收仍属于后续 M6。

可以检查 packaged executable 的 manifest 是否具备合理长路径能力，
但不得在本 Issue 构建安装器或修改系统策略。


二十四、稳定错误模型
--------------------

建立有限稳定错误码，至少表达：

- ROOT_PATH_INVALID
- ROOT_IS_FILESYSTEM_ROOT
- ROOT_NOT_OWNED
- ROOT_FORMAT_UNSUPPORTED
- ROOT_LAYOUT_CONFLICT
- PATH_INVALID
- PATH_OUTSIDE_ROOT
- PATH_LINK_NOT_ALLOWED
- FILE_NAME_INVALID
- FILE_TYPE_NOT_REGULAR
- FILE_TOO_LARGE
- FILE_CHANGED_DURING_COPY
- FILE_ALREADY_EXISTS_CONFLICT
- FILE_MISSING
- FILE_INTEGRITY_MISMATCH
- WRITE_ABORTED
- WRITE_FAILED
- PATH_CAPABILITY_UNSUPPORTED

名称可按现有约定调整。

错误对外 DTO：

- code
- 简短中文 message
- retryable
- 可选安全 context

不得包含：

- stack；
- 完整绝对路径；
- 用户名；
- 环境变量；
- SQL；
- 文件正文；
- 请求头；
- 密钥。

内部测试可以断言底层 cause，但生产日志仍需脱敏。
