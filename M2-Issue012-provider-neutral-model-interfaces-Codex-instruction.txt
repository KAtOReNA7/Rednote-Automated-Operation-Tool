七、核心 Provider 接口
----------------------

至少定义：

interface TextGenerationProvider
interface StructuredGenerationProvider
interface VisionProvider
interface ImageGenerationProvider

可以用一个组合 Provider 实现多个接口，但各方法和返回类型必须独立。

建议方法语义：

- generateText(request, context)
- generateStructured(request, schema, context)
- analyzeVision(request, context)
- generateImage(request, context)

不得在本轮加入：

- search()
- embed()
- ocr()
- batch()
- runTool()
- executeComputerUse()

每个调用必须显式接收：

- providerId；
- modelId；
- requestId；
- operation kind；
- input；
- generation options；
- timeout；
- AbortSignal；
- capability snapshot；
- protocol mode；
- secret-free trace metadata。

modelId 不允许默认值或 fallback。缺失时返回 PROVIDER_MODEL_NOT_CONFIGURED。

base URL 不由每个 request 任意传入；由受验证的 ProviderRuntimeConfig 装配。


八、配置装配
------------

ProviderRuntimeConfig 只允许来自 Issue 010 设置：

- protocol=OPENAI_COMPATIBLE；
- normalized base URL；
- research model ID；
- writing model ID；
- review model ID；
- optional embedding model ID；
- image model ID；
- credential reference=CONTENT_AI_API_KEY。

本轮不新增模型字段或数据库 migration。

ProviderConfigLoader：

- 从 SettingsRepository/SettingsService 的 main-only 端口读取；

- setup state 必须至少为 PROVIDER_CONFIGURED_UNVERIFIED；
- 不把 PROVIDER_CONFIGURED_UNVERIFIED 当作 verified。

CredentialResolver：

- 只定义端口；
- secret 仅在调用开始时按固定 reference 解析；

- finally 中解除引用；

- Issue 012 生产 wiring 不主动调用真实 resolver；

定义：

CapabilityState =

- UNKNOWN
- SUPPORTED
- UNSUPPORTED

ProviderCapabilities 至少包含：

- text；
- structuredJson；
- toolCalling；
- webSearch；
- imageGeneration；
- vision；
- batch；
- usage；
- streaming；
- maxContextTokens，可空；
- observedAt，可空；
- source，固定为 CONFIGURED_UNKNOWN/MOCK/PROBED 之一。

Issue 012：

- 默认实际中转站能力全部 UNKNOWN；
- Mock 可以显式声明 SUPPORTED/UNSUPPORTED；
- 不根据 model ID、URL、provider 名称或历史经验推断；
- 不持久化能力；
- 不发探测请求；
- 不选择最佳 endpoint；
- 不把 UNKNOWN 当作 SUPPORTED；
- 不把 UNKNOWN 永久写成 UNSUPPORTED。

如果生产调用需要的能力为 UNKNOWN 或 UNSUPPORTED，默认拒绝并返回稳定错误。Issue 013
探测后才允许真实调用。


十、协议模式
------------

定义明确、不可自动猜测的 protocol mode：

- RESPONSES
- CHAT_COMPLETIONS
- IMAGES_GENERATIONS
- MOCK

不得根据模型名推断 mode。

Responses codec、Chat Completions codec、Images codec：

- 分别编码；
- 分别解码；
- 不互相偷偷 fallback；
- 不在收到 404 后自动改 endpoint；
- 不自动试遍全部 endpoint；
- 不做 capability probe；
- 不允许任意 path；
- endpoint path 由受控枚举决定；
- Base URL 合并保留用户合法 base path；
- 禁止 userinfo、query、fragment；
- redirect=error；
- 不跟随跨域或同域 redirect。

Issue 013 才决定某个中转站/模型支持哪种 mode。


十一、文本与消息合同
--------------------

文本 request 使用供应商无关内容模型。

允许 message role：

- SYSTEM
- USER
- ASSISTANT

允许文本 part。Vision request 额外允许 image part。

限制：

- message 数量有上限；
- 单 part 和总字符数有应用级上限；
- 空白-only input 被拒绝；
- 控制字符策略明确；
- 不接受任意 provider JSON；
- 不接受调用方注入 Authorization/header/endpoint；
- 不接受 remote file URL；
- 不接受绝对本地路径；
- 不接受 file://；
- 不接受 tool definition，本轮无工具执行。

TextGenerationResult 至少包含：

- text；
- finishReason，统一枚举；
- refusal，可空且结构化；
- usage；
- providerRequestId，可空；
- modelId；
- protocolMode；
- latencyMs；
- outputTruncated=false/true；
- warnings，有限稳定代码。

不得返回供应商完整 raw response 给 workflow。


十二、结构化输出
----------------

StructuredGenerationProvider 必须支持调用方提供的、版本化 Schema：

- schemaId；
- schemaVersion；
- JSON Schema 或 Zod runtime validator；
- strict object；
- size/depth/array/string limits；
- deterministic validation result。

若仓库没有合格 runtime validator，可以新增 Zod，要求：

- package-lock 精确锁定；
- 只在需要的包声明；
- audit 0 vulnerabilities；
- 不引入 OpenAI SDK 作为结构化验证前提。

结构化调用流程：

1. 编码受控 Schema；
2. 调用 transport；
3. 识别 provider refusal；
4. 提取候选 JSON；
5. 严格 JSON.parse；
6. runtime Schema 校验；
7. 返回已验证 T；
8. 丢弃 raw provider envelope。

错误分类：

- PROVIDER_INVALID_JSON；
- PROVIDER_SCHEMA_VALIDATION_FAILED；
- PROVIDER_REFUSAL；
- PROVIDER_OUTPUT_TOO_LARGE；
- PROVIDER_UNSUPPORTED_STRUCTURED_OUTPUT。

错误不得携带：

- raw JSON；
- prompt；
- 整段 output；
- Schema 中的业务值；
- stack；
- credential。

只允许：

- schemaId/version；
- 有限 issue path；
- issue code；
- byte/character count；
- SHA-256 content hash；
- requestId。

不自动发送“修复 JSON”的第二次付费请求。本轮错误可恢复是指稳定分类、队列可安全决定
重试/人工处理，而不是隐式产生第二次费用。


十三、视觉输入
--------------

VisionProvider 输入只接受内存 binary part，不接受路径或 URL：

- Uint8Array；
- MIME allowlist：image/png、image/jpeg、image/webp、image/gif；
- 每张大小上限；
- 总大小上限；
- 图片数量上限；
- 空文件拒绝；
- magic bytes 与 MIME 基础一致性检查；
- 不解析 EXIF；
- 不自动上传到远程文件服务；
- 不把图片写入日志、error、DB 或 snapshot。

接口层只把 binary part 交给 codec。Issue 012 不从 ProjectDataRoot 读取正式图片，也不写
assets。

Vision result 使用与 Text result 相同的规范文本/usage/refusal 结构。


十四、图片生成输出
------------------

ImageGenerationProvider request 至少包含：

- prompt；
- modelId；
- count，应用级上限；
- size hint，可选受控枚举；
- quality hint，可选受控枚举；
- transparentBackground hint，可选三态；
- timeout/AbortSignal。

这些是供应商无关 hint，不保证所有 provider 支持。UNKNOWN capability 时不得真实调用。

ImageGenerationResult 至少包含：

- images 数组；
- 每张 MIME；
- inline bytes 或受控 opaque reference；
- width/height，可空；
- revisedPrompt，不默认公开且可空；
- usage；
- providerRequestId；
- warnings。

安全要求：

- base64 解码前先检查长度；
- 单张与总 output bytes 有上限；
- MIME/magic bytes 校验；
- 拒绝 data URL 中非 allowlist MIME；
- 不自动抓取 provider 返回的任意远程 URL；
- URL-only 响应返回 PROVIDER_UNSUPPORTED_OUTPUT_VARIANT；
- 不写入文件仓库；
- 不创建 assets 行；
- 不输出图片到测试报告；
- Mock 只返回极小、合法、合成图片 fixture bytes。

正式图片保存和处理属于后续图片 Issue。


十五、统一 usage
---------------

定义 ProviderUsage：

- inputTokens: integer|null；
- outputTokens: integer|null；
- totalTokens: integer|null；
- cachedInputTokens: integer|null；
- reasoningTokens: integer|null；
- imageInputCount: integer|null；
- imageOutputCount: integer|null；
- providerReported: boolean；
- complete: boolean；
- warnings: 稳定代码数组。

规则：

- 所有数字必须为有限非负安全整数；
- 缺失保持 null；
- 不把缺失写成 0；
- 不推测 token；
- 不按字符数估算 token；
- 不虚构 total；
- provider total 与分项冲突时保留可验证分项并产生 warning，或按明确合同拒绝；
- unknown extra usage 字段不透传；
- usage=false/UNKNOWN 时不得声称完整；
- 不计算美元；
- 不读取价格；
- 不写 cost_ledger；
- 不写 model_runs；
- Issue 014 才处理缓存和费用。


十六、HTTP transport
--------------------

实现可注入 HttpTransport。生产默认可以使用 Node.js 24 fetch，但不得在 app 启动时创建
请求。

要求：

- URL 只能由 normalized Base URL + 受控 endpoint 构造；
- HTTPS，或 Issue 010 已允许的 loopback HTTP；
- POST only；
- redirect=error；
- credentials=omit；
- 不使用 Cookie；
- 不使用系统/环境变量中的代理配置；
- 不允许调用方提供任意 header；
- Authorization 由 credential resolver 在最后一层注入；
- Content-Type/Accept 固定 application/json；
- request body 有字节上限；
- response header/body 有上限；
- 流式读取并计数；
- 非 JSON Content-Type 安全拒绝，图片 bytes endpoint 例外由 codec 明确处理；
- AbortSignal；
- deadline timeout；
- socket/DNS/TLS/HTTP 错误归一；
- response 完成或失败后释放资源；
- 不记录 raw request/response。

本轮不把 transport 接到 Electron 启动、local API 或真实工作流。

测试只允许：

- Scripted fake transport；
- 127.0.0.1、随机端口、测试进程内 fake provider server。

任何测试访问非 loopback 地址都必须失败。


十七、错误与恢复语义
--------------------

定义稳定 ProviderError，不把 vendor message 直接外泄。

至少包含：

每个错误包含：

- code；
- retryDisposition；
- outcomeCertainty；
- retryAfterMs，可空且有上限；
- requestId；
- providerId；
- modelId，可空；
- operation；
- finite safe details；
- cause category，不含原始异常文本。

retryDisposition：

- DO_NOT_RETRY
- RETRY_AUTOMATIC_SAFE
- RETRY_QUEUE
- RETRY_MANUAL

outcomeCertainty：

- NOT_SENT
- REJECTED_BEFORE_EXECUTION
- MAY_HAVE_EXECUTED
- COMPLETED_INVALID_OUTPUT

保守原则：

- 建连前失败可以安全自动重试；
- 明确 429/503 且响应表明未执行，可以按 Retry-After 进入队列；
- 请求发送后的断连、读取 timeout 或未知 5xx 默认 MAY_HAVE_EXECUTED；
- MAY_HAVE_EXECUTED 不自动重发，避免潜在重复费用；
- invalid JSON/schema 是 COMPLETED_INVALID_OUTPUT，不自动付费修复；
- 401/403/大多数 4xx 不重试；
- AbortSignal 取消不重试；
- 不假设中转站支持 idempotency key。


十八、有限重试协调
------------------

ProviderRetryPolicy 使用可注入 clock/random/backoff：

- 自动尝试总数默认最多 2；
- 仅对 RETRY_AUTOMATIC_SAFE；
- 指数退避；
- 有界 jitter；
- 解析整数秒或 HTTP-date Retry-After；
- Retry-After 上限 60 秒；
- AbortSignal 可中断 backoff；
- deadline 覆盖所有尝试总时间；
- 不使用真实 sleep 的单元测试；
- 不在 Provider 层调用 JobQueue；
- 只返回给未来 JobHandler 可消费的 retry metadata。

Issue 009 的 at-least-once 语义保持。未来真实 handler 必须处理幂等和
MAY_HAVE_EXECUTED，本轮不注册任何真实 handler。
