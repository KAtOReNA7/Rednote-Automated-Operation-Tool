三、产品政策与诚实边界

1. FULL_TRICK_ANALYSIS 被明确允许。核心诡计、凶手、结局和关键逻辑拆解本身不得成为失败、阻断或人工复核理由。
2. 检查目标是：
   - Brief 与 Draft 的剧透声明是否一致；
   - 所需警告是否存在、级别是否准确、是否落到正确表面；
   - NO_SPOILER / LIGHT_SPOILER 中是否出现有限规则能发现的可疑答案式表达。
3. PASS 的唯一含义是：
   “本版本的确定性声明与警告子集通过，且有限规则未发现需复核证据。”
4. PASS 绝不等于：
   - 已证明全文无剧透；
   - 已理解所有剧情语义；
   - 可以导出或发布；
   - 封面视觉警告已经显著。
5. 同义改写、代词指代、隐喻、跨段推理、身份反转、真实凶手/结局判断，以及警告与正文语义的完整等价性，均不在确定性能力承诺内。
6. 不能确定时进入 REVIEW_REQUIRED，不得扩大关键词表伪装语义能力，也不得静默 PASS。
7. AI 标识固定保持 false。AI 参与程度与版权风险不得进入本检查的输入 hash、finding、状态、评分、保存、优先级、排期、审批或未来聚合门禁。

四、实施范围

复用现有 DraftVersion、BriefVersion、冻结 spoiler plan、public artifact materialization/locator、quality_checks、Issue 027 的安全确认形状和 Copy 工作台。

必须实现：

1. 纯确定性 spoiler evaluator 与版本化 checker 常量。
2. 当前 Draft/Brief truth query、精确 freshness 和 append-only SPOILER 摘要仓储。
3. 两个且仅两个新 IPC：
   - quality:spoiler:preview
   - quality:spoiler:confirm
4. preview 只读；confirm 使用短期、单次、sender/window/draft/version/revision/inputHash 绑定令牌，并在 main 中重新读取和重算。
5. Copy 工作台中的一张紧凑 SPOILER 卡片；不得新增路由或独立页面。
6. PASS、BLOCKED、REVIEW_REQUIRED 三种保存结论；STALE、NOT_RUN 为查询派生状态，不新增数据库枚举。
7. content-addressed、append-only 保存：INSERT OR IGNORE 后回读逐字段核验；碰撞或不一致 fail closed。
8. 有界 finding，只保存 allowlist 元数据、surface/artifact identity、Unicode code-point 范围、text hash、reason code 和规则版本。
9. Draft/Brief current pointer、revision、input/lock hash、spoiler plan 或 invalidation 变化后，旧结果必须精确变为 STALE。

不得实现：

- 新 package、依赖、表、trigger、migration、队列、worker 或任务恢复框架；
- 模型、Search、Fetch、图片、OCR、网络、真实 API 或费用调用；
- 自动改写正文、自动补警告、审批、导出、发布或平台自动化；
- 封面渲染显著性判断；
- 完整剧情真相库或人工裁决系统；
- 第三个 IPC；
- Issue 029/030 的聚合或隐藏入口；
- 对 Issue 027 框架进行大规模泛化或复制。

只有无业务枚举、已出现至少两次、能明显减少重复的小型内部 helper 才允许抽取。不得新建“通用质量平台”。

五、确定性规则

1. 只处理 current、不可变、结构有效且可进入质量管线的 DraftVersion。
2. Draft 冻结的 Brief id/version/input hash/lock hash/spoiler plan 必须与当前 Brief 可核验事实一致；明确不一致为 BLOCKED。
3. 任一 Draft/Brief invalidation、current pointer 变化或依赖 hash 变化都会使旧摘要 STALE。
4. NO_SPOILER：placement 必须为 NONE，reveal flags 全部为 false，四个 warning 字段为空；明确矛盾为 BLOCKED。
5. LIGHT_SPOILER：placement 为 BODY_OPENING，不得声明揭示核心诡计或结局；正文开头警告存在且明确表达轻度范围。缺失或明确写成 FULL 级警告为 BLOCKED。
6. FULL_TRICK_ANALYSIS：Brief 已确认，reveal flags 符合冻结合同；封面、标题、正文开头及当前 Copy 合同要求的置顶评论警告均存在，且明确表达完整/核心诡计/结局范围。缺失或降级为轻度警告为 BLOCKED。
7. FULL 分支不运行公开内容泄露 detector。合成正文即使直接包含凶手、结局、核心诡计等文字，也必须在声明与警告正确时 PASS。
8. 标题 marker 必须实际包含在当前所选标题。正文开头只验证专用字段和结构契约，不猜测 CSS 或最终视觉。
9. NO/LIGHT 仅运行窄、版本化词法候选规则，并复用 NFC、换行规范化和 Unicode code-point locator。
10. 问句、否定、引用、反例、书名/人名、元讨论、上下文不完整、笼统“剧透预警”或扫描截断等无法确定场景，进入 REVIEW_REQUIRED 或明确的有限排除规则。
11. 候选不得被声明为作品真实答案或事实证据。
12. finding 数量、扫描字节和 details_json 必须有界；达到截断上限时不得 PASS。

六、数据与安全合同

1. 复用 quality_checks.check_type = SPOILER；0 Schema 变更。
2. 保存字段使用现有 draft_id、draft_version_id、result、severity、details_json、checker_version、input_hash、legacy_unresolved=0。
3. 不借用 Fact Mapping 专用 summary_status/reason_code 数据库枚举；领域状态与有限 reason 存在有界 details 中。
4. input hash 至少覆盖：
   - Draft id/revision/current version/status/structural validity/invalidation 摘要；
   - materialized artifact kind/order/work id/code-point length/text hash；
   - 四个 warning surface 的 presence/text hash；
   - Draft 冻结 Brief lineage、hash 与 spoiler plan；
   - 当前 Brief pointer/readiness/invalidation/hash 与 spoiler plan；
   - spoiler policy、Draft contract、normalization/locator、warning classifier、candidate detector 与 checker 版本。
5. input hash 不得包含时间戳、随机值、原文、AI 标识、版权风险、模型信息或密钥。
6. SQLite、IPC、日志、audit、诊断和证据文档不得保存/输出正文、警告全文、凭据、请求头、绝对路径或 SQL。
7. Renderer 只能使用两个窄 preload 方法；不得导入 Node/Electron/SQLite/fs/net/crypto。
8. DTO 必须 exact-object 校验、大小受限，并复用现有 sender frame/origin/BrowserWindow 绑定安全策略。
