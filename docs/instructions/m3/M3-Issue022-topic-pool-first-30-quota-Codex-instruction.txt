## 五、Topic Candidate V1

定义严格、版本化 TopicCandidate：

* topic identity/version；
* content type；
* 一个或多个 Work/Expression/Edition 引用；
* 有界 topic angle；
* 有界 central question 或 candidate judgment；
* analysis mode；
* spoiler level；
* required public labels；
* Dossier 与 ExpressionPermission 依赖；
* evidence/readiness 摘要；
* semantic fingerprint；
* eligibility；
* score breakdown；
* state、revision、provenance 和 timestamps。

候选只表示“可进一步开发的选题”，不等于 Content Brief、Draft 或已批准内容。

`topic angle` 与 `candidate judgment`：

* 只能是研究方向或待验证判断；
* 不能作为公开事实；
* 不能声称用户亲自读过；
* 不能包含无 Evidence 支撑的新事实；
* 不能复制整段 Evidence 或 Dossier 正文；
* 后续 Issue 024 仍需独立建立 Brief 和事实映射。

候选引用数量必须有界：

* 单书类型精确引用 1 个主要 Work；
* 横向比较至少 2 个、至多有限数量的 Work；
* 网络/出版比较至少包含两种表达或出版形态；
* 文化现象类型必须绑定可追溯的 Work 和研究主题，不接受纯泛热点空题。

## 六、资格规则

实现纯确定性 `TopicEligibilityPolicyV1`。

通用合格条件：

* 所有主要 subject 当前存在；
* 所需 Dossier current 且非 stale；
* 所需事实满足 Dossier/FactPolicy；
* ExpressionPermissionSnapshot current；
* 选定 analysis mode 获得权限；
* spoiler policy 完整；
* 不存在会否定该选题核心判断的 `FACT_BLOCKED`；
* dependency/policy versions current。

类型附加规则：

1. 不剧透单书判卷

   * Work 的 Dossier 必须 `READY_FOR_CONTENT_BRIEF`；
   * spoiler level 必须 `NO_SPOILER`；
   * 允许 PERSONAL 或 PUBLIC_RESEARCH 模式，但必须遵守各自标签和权限。

2. 完整诡计与逻辑拆解

   * Work Dossier 必须 ready；
   * spoiler level 必须 `FULL_TRICK_ANALYSIS`；
   * Issue 021 要求的 warning placement/confirmation 必须进入候选元数据；
   * 完整剧透本身不构成阻止理由。

3. 横向比较

   * 所有主要 Work 均需满足各自研究就绪；
   * 比较维度必须存在于有限 registry；
   * 不允许只因书名相似而建立比较；
   * 各 Work 的真实性模式可不同，但公开标签必须可同时满足。

4. 网络悬疑与出版推理比较

   * 必须有可核验的形态分类；
   * 至少一个网络表达与一个出版表达；
   * 不得用 publication relationship 参与产品门禁、评分或优先级；
   * 关系只作为选题内容的受控事实输入。

5. 推理小说与文化现象

   * 必须绑定至少一个 ready Dossier；
   * 文化现象或社会背景只能来自可追溯 Source/Claim 或 context；
   * context-only 可以启发 angle，但不能被写成已验证关键事实；
   * 纯热点、粉圈争议或无书目主体的候选不合格。

资格状态至少包括：

* `ELIGIBLE`
* `DOSSIER_NOT_READY`
* `AUTHENTICITY_BLOCKED`
* `FACT_BLOCKED`
* `STALE`
* `INSUFFICIENT_COMPARISON_SET`
* `SPOILER_POLICY_INCOMPLETE`
* `DUPLICATE`
* `ARCHIVED`

AI 参与度、AI 标识、版权信息不得进入资格规则。

## 七、可解释排序 V1

排序只在 `ELIGIBLE` 候选中进行，使用精确整数和版本化规则，不使用 SQLite REAL。

至少输出五个独立分量：

* `EVIDENCE_SUFFICIENCY`
* `CONTENT_FIT`
* `DIFFERENTIATION`
* `ESTIMATED_COST`
* `APPROVAL_WORKLOAD`

每个分量必须有：

* 0—10000 或等价整数值；
* reason codes；
* 输入依赖；
* policy version；
* unknown/known 状态。

冻结规则：

* Evidence 由 Dossier coverage、gap、stale、conflict 等确定性数据计算；
* Content fit 由内容类型、主体数量、可用表达模式和栏目要求计算；
* Differentiation 只和当前 TopicPool/历史 topic semantic fingerprint 比较；
* 不把模型生成措辞新颖度当成事实差异；
* Cost 显示预计本地/模型请求和预算状态，无法定价时保持 UNKNOWN；
* Approval workload 使用版本化工作量单位或分钟估计，不能伪造精确人工耗时；
* UNKNOWN 不能自动当作最佳或零成本；
* 排序总分、权重和 tie-break 完全确定；
* 相同输入乱序后结果一致；
* 锁定状态影响配额选择，不改写原始 ranking score；
* 搁置或归档不通过惩罚分实现，而通过状态过滤；
* AI 标识、版权、出版归属和普通负面观点不参与排序。

不得使用尚未存在的真实运营指标、虚构热度或平台推荐算法信号。

## 八、去重与差异性

定义确定性的 `TopicSemanticFingerprintV1`，至少包含：

* content type；
* canonical subject set；
* comparison dimension；
* spoiler level；
* analysis mode；
* normalized angle intent；
* policy version。

要求：

* 同主体、同类型、同角度的轻微措辞变化不能形成多个独立候选；
* 同一 Work 可以拥有不同且真实可解释的内容角度；
* 横向比较 subject 顺序变化不产生新候选；
* fingerprint 冲突时保留 provenance，并选择 canonical candidate；
* 用户锁定候选不会被自动合并或覆盖；
* archive 后重新发现应关联历史，不静默新建重复项；
* 去重不扫描全表 O(n²)，使用索引或候选集；
* 近似差异只能作为解释或人工判断，不以单一阈值自动删除。

## 九、候选生成边界

候选生成必须有纯本地确定性路径：

* 基于当前 ready Dossier、有限 section/entry、真实性权限和内容类型模板；
* 输出结构化候选，不生成完整文案；
* 不配置模型时仍可产生基本候选和首批配额计划。

可选增加 provider-neutral `TopicProposalV1`：

* 只通过 ModelExecutionService；
* 只发送用户明确选择的有界 Dossier 摘要或 Claim 引用；
* structured capability 必须 current、SUPPORTED；
* 输出 strict schema；
* 每个 angle 必须引用输入 subject/entry；
* 模型输出仍是 candidate，必须经过 runtime eligibility、去重和用户确认；
* prompt injection 不得修改 quota、policy、事实或权限；
* 不允许模型决定用户读过、评分来源或事实状态；
* 不允许输出标题、正文、标签或 Brief；
* 测试只使用 Scripted Mock，真实调用和费用为 0。

不要为了调用模型而扩大 Issue 022；若可选路径不能安全完成，可冻结合同和真实 UI 状态，但纯本地路径必须完整。

## 十、状态机与人工控制

TopicCandidate 状态至少包括：

* `PROPOSED`
* `LOCKED`
* `HELD`
* `ARCHIVED`

如计划成员需要独立状态，可使用 `SELECTED_IN_PLAN`，但不得混淆为候选本体已批准。

支持：

* lock；
* hold；
* resume；
* archive；
* restore；
* 批量操作。

所有变更必须：

* 使用 expected revision；
* preview before/after；
* 明确用户确认；
* sender/window 绑定、短期、单次 token；
* 事务和 append-only audit；
* 支持 undo/restore；
* 并发 stale fail closed；
* 不触发 Content Brief、Draft 或模型任务。

锁定语义：

* 锁定候选在满足资格时优先进入对应类别配额；
* 锁定不绕过资格；
* 同一 quota slot 存在过量锁定时，计划返回冲突，由用户处理；
* 系统不得静默解锁、丢弃或跨类别迁移。

## 十一、First-30 Plan V1

定义版本化、不可静默改写的 `TopicQuotaPlanV1`：

* quota profile/version；
* pool snapshot hash；
* ranking policy version；
* selected topic IDs；
* per-category selected/required/shortfall；
* locked/held/archived counts；
* score/eligibility snapshot；
* total estimated cost/workload；
* status、revision、previous version、createdAt；
* plan reason/warnings。

状态至少包括：

* `PREVIEW`
* `COMPLETE`
* `INCOMPLETE`
* `STALE`
* `SUPERSEDED`

求解顺序必须确定：

1. 验证 current eligibility；
2. 每类先放入合格 LOCKED 候选；
3. 对剩余候选按该类 ranking 和稳定 tie-break 选择；
4. 不跨类补位；
5. 输出 shortfall；
6. 保存精确选择理由。

要求：

* 完整计划精确 30 项且分配为 10/8/6/3/3；
* 同一 candidate 不能占多个 slot；
* 同一 semantic fingerprint 不能重复入选；
* 可配置每个 Work 在计划中的最大曝光次数，规则版本化；
* 计划输入变化后标记 stale，不自动重排；
* 用户明确重建后创建新版本，旧版本保留；
* 相同输入为 deterministic no-op；
* 失败或取消不替换 current plan；
* Issue 022 不把计划转成日历、发布排期或实验。
