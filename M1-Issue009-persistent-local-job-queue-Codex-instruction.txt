五、交付语义：不得承诺 exactly-once
-----------------------------------

任务队列必须明确记录其交付语义：

at-least-once execution with durable idempotent enqueue and lease protection

也就是：

- 正常运行时，同一任务不能被两个 worker 同时领取。
- 同一幂等键不能重复创建逻辑相同的任务。
- 进程崩溃后，租约过期的任务可以恢复。
- 但如果未来某个任务在完成外部副作用后、写入完成状态前崩溃，
  该任务仍可能被再次执行。

因此不得在代码、ADR、README 或报告中宣称：

- exactly once
- 绝对不会重复执行
- 外部副作用天然只发生一次

未来所有产生费用或外部副作用的任务处理器必须自行使用业务幂等键、
model_runs、cost_ledger 或目标资源唯一约束实现幂等。

本 Issue 只提供队列基础，不实现上述业务处理器。

   负责应用启动时恢复过期租约。

6. QueueClock

7. BackoffPolicy
   可注入退避策略，支持确定性测试。

8. JobPayloadValidator

组件放置位置应符合现有 monorepo 边界。

- 数据库 SQL 和仓储放在 packages/db
- 队列状态机、worker 和编排放在 packages/workflows

不得造成 packages/core 反向依赖 packages/db 或 workflows。


七、任务状态
------------

在检查现有 Core 定义后，建立一个单一权威的任务状态集合。

至少需要表达：

- QUEUED
- RUNNING
- PAUSE_REQUESTED
- PAUSED
- CANCEL_REQUESTED
- RETRY_WAIT
- SUCCEEDED
- FAILED
- CANCELLED

如果现有 Core 已有等价名称，优先复用，不得建立第二套语义不同的枚举。

合法转换至少包括：

1. 创建：
   无 → QUEUED

2. 领取：
   QUEUED → RUNNING
   RETRY_WAIT → RUNNING

3. 成功：
   RUNNING → SUCCEEDED

4. 自动重试：
   RUNNING → RETRY_WAIT
   RETRY_WAIT → RUNNING

5. 重试耗尽：
   RUNNING → FAILED

6. 排队状态暂停：
   QUEUED → PAUSED
   RETRY_WAIT → PAUSED

7. 运行中请求暂停：
   RUNNING → PAUSE_REQUESTED
   PAUSE_REQUESTED → PAUSED

8. 恢复：
   PAUSED → QUEUED

9. 排队或暂停状态取消：
   QUEUED → CANCELLED
   RETRY_WAIT → CANCELLED
   PAUSED → CANCELLED

10. 运行中请求取消：
    RUNNING → CANCEL_REQUESTED
    CANCEL_REQUESTED → CANCELLED

11. 过期租约恢复：
    RUNNING → RETRY_WAIT 或 FAILED
    PAUSE_REQUESTED → PAUSED
    CANCEL_REQUESTED → CANCELLED

终态：

- SUCCEEDED
- FAILED
- CANCELLED

终态不得被后台恢复器自动复活。

FAILED 的人工重试必须通过显式 API 进行，不得静默发生。

所有非法转换必须被领域层和数据库操作拒绝。


八、Schema 增量迁移
-------------------

先检查当前 jobs 表的真实字段和约束，再设计下一版增量迁移。

不得编辑、重写或重新计算已经提交的历史迁移。

必须使用一个新的、连续编号的不可变迁移。

为实现 Issue 009，jobs 至少需要支持以下语义：

- 调用方提供的 idempotency_key
- payload_hash
- priority
- status
- attempt_count
- max_attempts
- next_run_at 或等价可执行时间
- lock_owner
- lease_token
- lease_expires_at
- last_heartbeat_at
- pause_requested_at
- cancel_requested_at
- started_at
- finished_at
- last_error_code
- last_error 或安全错误摘要
- result_json，可选
- created_at
- updated_at
- revision 或等价并发保护字段，若设计需要

字段名称可以根据现有 Schema 调整，但语义不得缺失。

数据库约束至少包括：

1. idempotency_key 非空且唯一。
2. payload_hash 非空。
3. priority 有合理范围。
4. attempt_count >= 0。
5. max_attempts >= 1。
6. attempt_count <= max_attempts，或明确说明为什么需要允许等于/超过并用测试证明。
7. lease 相关字段在 RUNNING、PAUSE_REQUESTED、CANCEL_REQUESTED 时符合一致性。
8. 终态必须有 finished_at。
9. 非终态不得错误设置完成字段。
10. JSON 字段必须是合法 JSON。
11. 时间字段必须符合项目的 UTC 时间格式。
12. 状态必须来自 Core 权威集合。

如 SQLite ADD COLUMN 无法安全表达新约束，可以使用受控的表重建迁移。

表重建必须测试：

- 保留已有 jobs 数据
- 保留主键
- 保留外键
- 保留索引
- 保留创建和更新时间
- 不改变其他 25 张业务表
- 失败时完整回滚

十、幂等入队
------------

公开 API 至少实现：

enqueueJob(input)

input 至少包含：

- jobType
- idempotencyKey
- payload
- priority
- maxAttempts
- availableAt，可选

规则：

1. idempotencyKey 由调用方提供。
2. 系统保存规范化 payload 的稳定哈希。
3. 同一幂等键、同一 jobType、同一 payload 再次入队：
   返回已有任务，不创建新行。
4. 同一幂等键但 jobType 不同：
   抛出 IDEMPOTENCY_CONFLICT。
5. 同一幂等键但 payload 不同：
   抛出 IDEMPOTENCY_CONFLICT。
6. 并发两个连接使用同一幂等键入队：
   最终只能有一条任务记录。
7. 不允许用随机幂等键掩盖重复任务。
8. 不允许把完整 API 密钥、Authorization header 或其他凭据放进幂等键。

payload 规范化必须确定、可测试，不得受对象键顺序影响。


十一、原子领取与租约
--------------------

公开 API 至少实现：

claimNextJob(workerId, options)

要求：

1. 使用短事务原子领取。
2. 只领取：
   - QUEUED 且 next_run_at <= now
   - RETRY_WAIT 且 next_run_at <= now
3. 排序至少考虑：
   - priority 高者优先
   - next_run_at 早者优先
   - created_at 早者优先
   - 使用 id 作为最终确定性排序
4. 领取后设置：
   - RUNNING
   - lock_owner
   - 新 lease_token
   - lease_expires_at
   - last_heartbeat_at
   - started_at，首次执行时
   - attempt_count 增加
5. 同一任务不能被两个 worker 同时领取。
6. 两个独立 DatabaseSync 连接竞争时也必须成立。
7. 领取事务提交后才允许调用任务处理器。
8. 不得在领取事务内等待。

lease_token 用于防止旧 worker 或同名 worker 对新租约执行完成操作。

只使用 workerId 不足以证明租约所有权。


十二、心跳
----------

公开 API 至少实现：

heartbeat(jobId, workerId, leaseToken)

要求：

1. 只有当前租约所有者可以续租。
2. 过期租约不能被旧 worker 恢复。
3. leaseToken 不匹配时拒绝。
4. 终态任务拒绝心跳。
5. 心跳返回当前控制信号：
   - CONTINUE
   - PAUSE
   - CANCEL
6. 心跳更新必须是短事务。
7. 心跳失败不能静默忽略。


十三、完成和失败
----------------

公开 API 至少实现：

completeJob(jobId, workerId, leaseToken, result?)
failJob(jobId, workerId, leaseToken, error)

完成规则：

1. 只有当前有效租约所有者可以完成。
2. leaseToken 不匹配时拒绝。
3. SUCCEEDED 设置 finished_at。
4. 清除租约字段。
5. result 必须是合法、受大小限制的 JSON。
6. 重复 complete 调用必须有明确的幂等或冲突语义。

失败规则：

1. 保存稳定 error code 和安全错误摘要。
2. 不把完整 stack、请求头、密钥或巨大响应写入 jobs。
3. 如果 attempt_count < max_attempts：
   进入 RETRY_WAIT，并持久化 next_run_at。
4. 如果重试耗尽：
   进入 FAILED 并设置 finished_at。
5. 清除租约字段。
6. 失败和新状态必须在同一事务中写入。


十四、退避策略
--------------

实现可配置、可注入、可确定性测试的退避策略。

默认可使用：

- 指数退避
- 最大延迟上限
- 可选 jitter

要求：

1. 基础延迟、倍率、上限可配置。
2. 测试使用注入时钟和注入随机源。
3. next_run_at 在事务中持久化。
4. 应用重启后不能重新随机计算已经安排的时间。
5. 不允许负延迟。
6. 极大 attempt 值不能发生整数溢出。


十五、暂停、恢复和取消
----------------------

公开 API 至少实现：

requestPause(jobId)
acknowledgePause(jobId, workerId, leaseToken)
resumeJob(jobId)
requestCancel(jobId)
acknowledgeCancel(jobId, workerId, leaseToken)

暂停规则：

1. QUEUED/RETRY_WAIT：
   可直接进入 PAUSED。
2. RUNNING：
   进入 PAUSE_REQUESTED，由 worker 协作确认。
3. PAUSED：
   重复暂停应幂等。
4. resume：
   PAUSED → QUEUED。
5. resume 不得重置 attempt_count。
6. 终态不能暂停或恢复。

取消规则：

1. QUEUED/RETRY_WAIT/PAUSED：
   可直接进入 CANCELLED。
2. RUNNING：
   进入 CANCEL_REQUESTED，由 worker 协作确认。
3. CANCELLED：
   重复取消应幂等。
4. 取消后不得被 worker 领取。
5. 终态不得被取消请求复活。

不得使用强杀线程来伪装可靠取消。

worker handler 使用 AbortSignal 或等价协作机制。


十六、失败任务的显式人工重试
----------------------------

公开 API 至少实现：

retryFailedJob(jobId, options)

只允许 FAILED。

要求：

1. 必须显式调用。
2. 不删除历史 attempt_count。
3. 不修改原 idempotency_key。
4. 通过增加允许的 additionalAttempts 或等价设计保留历史。
5. 新的 maxAttempts 必须大于当前 attempt_count。
6. 设置新的 next_run_at。
7. 清除终态完成字段和安全错误摘要中的执行态信息，但保留审计记录。
8. 不得对 SUCCEEDED 或 CANCELLED 自动重试。


十七、崩溃与重启恢复
--------------------

实现：

recoverExpiredLeases(now)

只处理租约已经过期的任务。

规则：

1. RUNNING：
   - attempt_count < max_attempts → RETRY_WAIT
   - 否则 → FAILED
2. PAUSE_REQUESTED：
   → PAUSED
3. CANCEL_REQUESTED：
   → CANCELLED
4. 未过期租约不能恢复。
5. 终态不能恢复。
6. 恢复清除旧 lock_owner、lease_token、lease_expires_at 和 heartbeat。
7. 恢复动作写入 audit_events。
8. 多个进程同时恢复时，状态转换仍必须原子且只发生一次。

应用启动时可以调用恢复服务，但本 Issue 不接 Electron 启动流程。

只提供可复用的恢复入口和测试。


十八、JobWorker
---------------

实现一个不依赖 Electron 的本地 worker。

要求：

1. 默认并发数为 1，可配置。
2. 不允许无界并发。
3. 无任务时使用可配置轮询间隔。
4. 使用注入时钟或可控调度器测试。
5. 处理器运行时不保持数据库事务。
6. 定期心跳。
7. 接收 PAUSE/CANCEL 控制信号。
8. 处理器成功后调用 completeJob。
9. 处理器失败后调用 failJob。
10. 未注册 jobType：
    使用稳定错误码失败，不崩溃整个 worker。
11. worker 停止领取新任务后，支持受控关闭。
12. 超过关闭等待时间的执行中任务：
    不得伪造成功；依赖租约恢复或安全地进入重试。

本 Issue 的 handler registry 只使用测试处理器，例如：

- success handler
- fail-once handler
- always-fail handler
- slow cooperative handler
- pause-aware handler
- cancel-aware handler

不得加入研究、模型、图片、OCR 或平台处理器。

二十、Payload 与错误安全
------------------------

payload 必须：

- 可 JSON 序列化
- 有大小上限
- 有深度上限或等价防护
- 规范化后再计算 hash
- 不允许循环引用
- 不允许 undefined、function、symbol 等不可持久化值

至少拒绝明显凭据字段：

- apiKey
- api_key
- authorization
- password
- secret
- accessToken
- access_token
- refreshToken
- refresh_token

未来任务只能保存凭据引用名称，不能保存凭据值。

错误摘要：

- 有长度上限
- 不保存完整请求头
- 不保存完整 API 响应
- 不保存明文密钥
- 不保存用户未授权的大段内容


二十一、Audit 记录
-----------------

所有重要状态转换应在同一事务中写入 audit_events：

- ENQUEUED
- CLAIMED
- HEARTBEAT，是否每次记录由容量评估决定
- COMPLETED
- RETRY_SCHEDULED
- FAILED
- PAUSE_REQUESTED
- PAUSED
- RESUMED
- CANCEL_REQUESTED
- CANCELLED
- LEASE_RECOVERED
- MANUAL_RETRY

如果不记录每次 HEARTBEAT，必须说明原因，且仍需保留 last_heartbeat_at。

Audit 内容不得包含密钥或完整 payload。


二十二、数据库性能边界
----------------------

建立并验证适合以下查询的索引：

1. 下一个可领取任务：
   status + next_run_at + priority + created_at
2. 过期租约：
   status + lease_expires_at
3. 幂等键：
   idempotency_key unique
4. worker 当前任务：
   lock_owner + status
5. 按类型和状态查询：
   job_type + status

使用 EXPLAIN QUERY PLAN 或等价方法证明关键查询使用预期索引。

不得为了测试通过创建大量重复或无意义索引。


二十三、最低测试矩阵
--------------------

至少覆盖：

A. 起点和迁移

1. Issue 007 历史迁移校验和不变。
2. 新迁移版本连续。
3. 新迁移重复运行幂等。
4. 现有 jobs 数据在迁移后保留。
5. 新迁移失败时完整回滚。
6. 迁移前备份仍生效。
7. 其他业务表未发生无关改变。

B. 入队和幂等

8. 正常入队。
9. 延迟入队。
10. 同键、同类型、同 payload 返回同一任务。
11. 同键、不同类型冲突。
12. 同键、不同 payload 冲突。
13. 两连接并发同键只创建一条。
14. payload 对象键顺序不同但语义相同时 hash 一致。
15. 无效 JSON 类型被拒绝。
16. 超大 payload 被拒绝。
17. 明显凭据字段被拒绝。

C. 领取和租约

18. 领取最高优先级且已到期任务。
19. 未到 next_run_at 的任务不被领取。
20. PAUSED/CANCELLED/终态不被领取。
21. 两个 worker 不能领取同一任务。
22. 两个独立数据库连接竞争仍只有一个成功。
23. 领取增加 attempt_count。
24. 领取生成新 lease_token。
25. 非所有者不能心跳。
26. 旧 lease_token 不能操作新租约。
27. 心跳延长租约。
28. 过期租约不能由旧 worker 完成。

D. 完成和失败

29. 正常完成。
30. 重复完成的明确语义。
31. 失败后进入 RETRY_WAIT。
32. next_run_at 持久化。
33. 达到 max_attempts 后 FAILED。
34. 终态设置 finished_at。
35. 租约字段被清理。
36. result_json 大小和 JSON 约束。
37. 错误摘要截断和凭据清理。

E. 暂停、恢复和取消

38. QUEUED 直接暂停。
39. RETRY_WAIT 直接暂停。
40. RUNNING 请求暂停。
41. worker 确认暂停。
42. PAUSED 恢复为 QUEUED。
43. resume 不重置 attempt_count。
44. QUEUED/RETRY_WAIT/PAUSED 直接取消。
45. RUNNING 请求取消。
46. worker 确认取消。
47. CANCELLED 不再领取。
48. 终态非法转换被拒绝。

F. 重试和恢复

49. FAILED 显式人工重试。
50. 人工重试保留历史 attempt_count。
51. 人工重试增加可用 attempts。
52. SUCCEEDED/CANCELLED 不能人工重试。
53. 过期 RUNNING 恢复为 RETRY_WAIT。
54. 重试耗尽的过期 RUNNING 恢复为 FAILED。
55. 过期 PAUSE_REQUESTED 恢复为 PAUSED。
56. 过期 CANCEL_REQUESTED 恢复为 CANCELLED。
57. 未过期任务不恢复。
58. 多恢复器竞争只转换一次。
59. 数据库关闭重开后恢复行为一致。

G. Worker

60. success handler。
61. fail-once handler 自动重试后成功。
62. always-fail handler 最终失败。
63. 未注册 handler 不导致 worker 崩溃。
64. pause-aware handler。
65. cancel-aware handler。
66. worker 停止后不领取新任务。
67. 崩溃模拟后租约恢复。
68. 并发上限生效。

H. 性能与平台

69. 关键领取查询使用预期索引。
70. 过期租约查询使用预期索引。
71. 中文和空格 Windows 路径。
72. 多个 DatabaseSync 连接。
73. WAL 模式下状态一致。
74. 1,000 个待处理任务下领取顺序正确。

I. 冻结约束

75. ai_disclosure 仍固定 false。
76. 不存在版权检查或版权队列状态。
77. AI 参与程度不影响任务优先级、领取和状态。
78. 来源字段变化不影响队列调度。
79. 不存在小红书平台动作。
80. 不存在真实 API、云服务、开卷或盗版电子书处理。

不得用纯字符串搜索替代运行时行为测试。
